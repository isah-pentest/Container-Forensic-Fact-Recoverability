# Container Forensic Fact Recoverability

Protocol, tooling and analysis for the study **Forensic Fact Recoverability After Pod Termination:
Effects of Acquisition Timing and Background Event Load on Retained Kubernetes Audit and eBPF
Telemetry** (protocol FRX v3.0, amended v3.0.1).

**Status:** execution and analysis complete. The release cited by the article is tag
**`v1.0-submission`**; the cited analysis output set is the one named by that tag's commit
(`analysis_outputs/<first 12 characters of the commit>`) and is attached to the GitHub release.
The protocol was frozen and registered before the first confirmatory run (`protocol-v3.0.1-frozen`,
`protocol/registration.json`, <https://osf.io/b6rv9>). Gate records are in `protocol/gates/`.

## Objective

When a pod is deleted, the evidence of what it did survives only in logs kept outside the pod. These
are the API-server audit log and runtime telemetry (Tetragon, eBPF). Both are written to size-rotated
files, so older records are deleted as new ones arrive. The study asks:

- **RQ1.** How often can an investigator recover a complete record of a short pod lifecycle after the
  pod is gone? The lifecycle is: a pod is created, a nonce-tagged command is executed in it, and it is
  deleted.
- **H1.** Does acquisition timing (continuous follow vs one delayed copy) change that rate, and is the
  change larger under heavier background event load?
- **H2.** Does the same hold for the second source?
- **E3 (exploratory).** Does a closed-form headroom rule predict when records are lost? The rule is
  H = ((M − o) + kM) / W, where M is the store size, o the file offset, k the backups kept and W the
  bytes written before acquisition.
- **E4 (exploratory).** At which stage is each lost record lost?

The recovered facts are:

| Fact | Question | Sources |
|---|---|---|
| F1 | Which pod was created, with what UID? | audit |
| F2 | What executable and arguments were executed? | audit, Tetragon |
| F3 | Was the pod deleted (by the actor that performed the action)? | audit |

## Design

- **Design:** randomized complete blocks. Each block has 4 cells and 1 negative-control run, B = 16
  blocks, 80 runs.
  - Factor A, timing: C = continuous follower until T + g; D = one-shot copy at T + δ.
  - Factor L, load: L = low, M = moderate background event rate.
- **Operating points:** δ = 60 s, g = 10 s, ε = 5 s. Each store is 10 MiB × 1 backup. The load
  rates (audit and Tetragon, B/s) are L ≈ 43 k / 46 k and M ≈ 231 k / 250 k.
- **Primary endpoint and estimand:** Y = 1 if F1–F3 are all recovered (F2 under the union rule).
  The estimand is Δ_A, the difference of the D − C effect between M and L.
- **Analysis:**
  - Randomization test over block sign flips.
  - 95% CI chosen by a pre-specified structure rule; MOVER-Wilson is the fallback.
  - H2 is gated by a fixed sequence (tested only if H1 is rejected).
- **Seeding:** the master seed comes from a NIST Randomness Beacon pulse (`protocol/master_seed.json`).
- **Blinding:** reconstruction runs blinded in an isolated process, from the acquired bytes only.
  Truth is unsealed only after the answers are hashed. Scores are locked before any analysis.
- **Integrity:** packages are write-once with SHA-256 manifests and an attempt ledger, and an
  off-host replica is checked block by block.
- **Platform:** Kubernetes v1.37.0 (kind) and Tetragon 1.7.1, on an Ubuntu Server VM (Hyper-V).
  WSL2 is not a valid host; see `protocol/gates/G1.md`.

## Results (cited analysis set, release `v1.0-submission`)

| | LC | LD | MC | MD |
|---|---|---|---|---|
| Y = 1 | 16/16 | 16/16 | 16/16 | 11/16 |

- **H1:** Δ̂_A = −0.156, randomization p = 0.062, 95% CI [−0.312, 0.005] (MOVER-Wilson). Not
  rejected at α = 0.05: the timing × load effect is not distinguishable from zero at this precision.
  H2 was not tested (fixed sequence).
- **False attribution:** 0/95 negative-control and decoy identities (Clopper–Pearson upper bound 0.038).
- **E3:** the H < 1 rule classified every delayed-read run correctly (confirmatory and calibration
  series).
- **E4:** all 57 lost fact–source records were lost because rotation deleted them before the read
  (stage EVICTED).

## Reproducing the claims

### 1. Environment
```bash
git clone <this repository> && cd Container-Forensic-Fact-Recoverability
git checkout v1.0-submission        # the release whose commit names the cited output set
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.lock && pip install -e .
pytest                               # synthetic fixtures; no evidence needed
```
`requirements.lock` pins the direct dependencies (it is part of the frozen protocol and is not
edited). The complete environment in which the cited output set was generated (Python version,
platform and every installed distribution) is recorded in `protocol/gates/G7_ENVIRONMENT.md`
(`python3 -m frx.analysis environment`).

### 2. Verify the frozen protocol
```bash
python3 -m frx.analysis registered-freeze  # FREEZE.json at the frozen tag = registered SHA-256; every
                                           # protocol file and the code digest checked from git objects
python3 -m frx.analysis frozen-diff        # only the analysis layer and records changed after the freeze
```
`registered-freeze` lists any file named in `FREEZE.json` that is absent from the public history as
*withheld*, with its registered hash (see "What is public" below).

### 2a. Run the whole analysis without the study's evidence
```bash
python3 -m frx.analysis demo --out /tmp/frx-demo
```
This builds a small synthetic evidence store with the simulated cluster of the test suite
(`tests/fakecluster.py`: 2 blocks, 10 confirmatory attempts, 4 calibration runs), scores and locks it
as in production, then runs `all` and `rebuild-check` on it. The synthetic numbers have no meaning; the
point is that every command, table, figure and check runs end to end.

### 3. Regenerate everything from the evidence store
```bash
./reproduce.sh /path/to/frx-evidence
```
`reproduce.sh` stops at the first failing stage:
1. unit tests;
2. frozen-diff;
3. integrity re-verification of every package and the score lock;
4. re-running the frozen blinded reconstruction and scoring on all 96 packages, where every locked
   answer and score must match byte for byte;
5. regenerating every analysis, table and figure, then comparing the result with the cited set
   `analysis_outputs/<commit>` of the checked-out release.
6. recomputing the published quantities from the regenerated run-level table (`rebuild-check`).

The final line should read `regenerated output set is identical to …`.

### 4. Individual commands
```bash
python3 -m frx.analysis status        --evidence DIR   # execution state from dispositions only
python3 -m frx.analysis verify        --evidence DIR   # manifests, score lock, analysis input hash
python3 -m frx.analysis rescore-check --evidence DIR   # frozen scoring reproduced byte for byte
python3 -m frx.analysis all           --evidence DIR   # results.json, tables, figures, claims register
python3 -m frx.analysis compare A B                    # compare two output sets
python3 -m frx.analysis compare A B --ignore-commit    # ... accepting only each set's own commit identifier
python3 -m frx.analysis audit-sample  --evidence DIR   # seeded raw-to-fact audit worksheet
python3 -m frx.analysis rebuild-check RUN_LEVEL_CSV RESULTS_JSON   # published quantities from the run-level table alone
```

### 5. From a claim to its evidence
`analysis_outputs/<commit>/claims_register.csv` lists one row per headline number. Each row gives the
estimand, the metric IDs, the function that computes it, the table or figure that shows it, the run IDs
behind it and the artifact paths. `results.json` holds every computed value. `SHA256SUMS` covers the set.

### 6. Run-level dataset
`analysis_outputs/<commit>/data/run_level.csv` has one row per attempt of the confirmatory cohort and
the calibration series: block, slot, assigned condition, arm and load, disposition, target and measured
write rates, observed acquisition delay, every fact-source state, the union states, `Y`, the control
checks and, for each delayed read, the headroom `H`, the formula loss probability and the loss stage of
each primary fact-source pair. `data/data_dictionary.csv` gives the type, unit, allowed values,
definition and recorded source of every column. `rebuild-check` recomputes the published quantities
(cell counts, the frozen primary analysis, run accounting, per-fact and per-source recovery, controls,
delays, write rates, headroom accuracy, Brier scores and loss stages) from these two files and
`results.json` only, and `data/rebuild_check.json` records the result for the cited set.

## Ground rules

- **Self-contained.** The repository was initialized empty; no earlier code, data or result is an input.
- **No machine learning.**
  - Operating points come from a closed-form formula.
  - Randomization uses a seeded PRNG.
  - Reconstruction is a deterministic rule-based matcher.
  - Inference uses randomization and classical statistics.
- **Analysis after the freeze is confined to `src/frx/analysis/`.** `frozen-diff` checks this.
- **Every reported number comes from a repository command.**
